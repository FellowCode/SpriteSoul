# Sprite Soul — Technical Specification

## 1. Цель

Создать локальное Windows-приложение для генерации **Depth Map** и **Normal Map** из PNG-спрайтов и PNG-атласов для 2D/2.5D игры.

Типичные объекты: деревья, здания, техника, персонажи, пропсы.

Главный приоритет — **качественные карты с точным соответствием исходному спрайту, при этом код должен оставаться простым, модульным и легко поддерживаемым**. Не строить enterprise-архитектуру, framework или избыточную систему проверок, но и не сокращать структуру проекта ценой читаемости и сопровождаемости.

Целевая видеокарта: **NVIDIA RTX 3060 Laptop, 6 GB VRAM**.

---

## 2. Основной pipeline

```text
PNG / Atlas
    ↓
Depth AI
    ↓
Depth processing / manual correction
    ↓
FINAL DEPTH
    ↓
Normal from Depth
    ↓
Lighting Preview
    ↓
Export
```

**Depth — единственный источник геометрии для Normal Map.**

Normal Map не должна независимо генерироваться AI/diffusion-моделью. Она вычисляется математически из финальной Depth Map, чтобы Depth и Normal всегда описывали одну поверхность.

---

## 3. Обязательное соответствие исходнику

Исходный PNG является источником:

- width/height;
- положения объекта;
- silhouette;
- прозрачных отверстий;
- alpha.

AI разрешено оценивать только геометрию/depth.

Нельзя:

- менять размер холста;
- перемещать или центрировать объект;
- менять масштаб;
- расширять или сужать silhouette;
- добавлять/закрывать прозрачные участки;
- использовать сгенерированную alpha вместо исходной.

На выходе карты имеют тот же размер, а alpha берётся непосредственно из source PNG.

---

## 4. Стек

Использовать простой Python-стек:

- **Python 3.11**;
- **PyTorch + CUDA** — Depth inference;
- **NumPy** — математика;
- **OpenCV** — фильтры, gradients, resize/tile processing;
- **Pillow** — PNG I/O при необходимости;
- **PySide6** — GUI.

Не подключать ComfyUI в основной продукт, если без него задача решается напрямую.

Не добавлять тяжёлые библиотеки без необходимости.

---

## 5. Depth AI

Использовать **одну** современную monocular-depth модель.

Предпочтительный первый вариант — актуальная реализация **Marigold**, но перед интеграцией проверить текущий API и доступные модели. Если существует более подходящая актуальная модель, которая лучше работает со стилизованными игровыми спрайтами и помещается в 6 GB VRAM, допускается использовать её вместо Marigold.

Требования:

- CUDA;
- FP16, где это безопасно;
- работа на RTX 3060 Laptop 6 GB;
- обработка больших изображений tiles/crops при нехватке VRAM;
- сборка результата строго в исходные координаты;
- понятная обработка CUDA OOM вместо падения программы.

Не создавать несколько ML-backend'ов в MVP. Код вызова модели просто отделить от остального pipeline так, чтобы модель можно было заменить позже.

---

## 6. Depth processing

AI Depth является исходной оценкой, а не окончательным результатом.

Нужны только практически полезные операции:

- Invert Depth;
- Depth Range / Strength;
- Contrast;
- Smooth;
- Raise brush;
- Lower brush;
- Smooth brush;
- Undo / Redo.

Все ручные инструменты меняют только Depth.

После изменения Depth Normal должна пересчитываться автоматически.

### Требование к качеству

Не превращать нарисованные тени, блики, текстуру древесины, отдельные листья, кирпичи и другие детали RGB-арта в сильный геометрический рельеф.

Для деревьев важнее крупная выпуклая форма кроны, форма ствола и ветвей.

Для зданий важнее правильные плоскости стен, крыши, скатов и крупных выступов.

Крупная форма всегда важнее мелкой текстуры.

---

## 7. Normal Map

Normal Map вычислять из **FINAL DEPTH**.

Базовый принцип:

```python
dzdx = derivative_x(depth)
dzdy = derivative_y(depth)

nx = -dzdx * strength
ny = -dzdy * strength
nz = 1.0

normal = normalize([nx, ny, nz])
```

Фактический знак Y проверить на синтетических slopes и зафиксировать корректную конвенцию.

Default output:

**Tangent-space OpenGL +Y**.

В GUI добавить:

- Normal Strength;
- OpenGL / DirectX.

DirectX должен получаться корректной инверсией Y/green относительно OpenGL.

### Silhouette

Нельзя считать прозрачный фон обычной depth=0 поверхностью при вычислении производных около края объекта — это создаёт ложный bevel по silhouette.

Перед вычислением gradient нужно корректно продолжить/распространить depth за край mask либо использовать masked derivative.

После расчёта Normal восстановить **точную исходную alpha**.

---

## 8. Атласы и большие изображения

Приложение должно принимать как отдельный PNG-спрайт, так и atlas.

Не создавать сложную систему автоматического semantic splitting в первой версии.

Приоритет:

1. попробовать обработать изображение целиком;
2. если не хватает VRAM — tiled inference;
3. при необходимости использовать alpha/components/crops;
4. собрать depth обратно строго в исходных координатах.

Tile/crop processing не должен менять положение спрайтов или размер atlas.

---

## 9. GUI

Сделать простой функциональный интерфейс на PySide6.

Минимальные действия:

```text
Open | Generate | Undo | Redo | Export
```

Основные режимы просмотра:

```text
Source | Depth | Normal | Lighting Preview
```

Нужны:

- zoom;
- pan;
- checkerboard transparency;
- настройки Depth;
- Normal Strength;
- OpenGL/DirectX;
- radius/strength кисти;
- Raise/Lower/Smooth brush.

Не тратить код на декоративный интерфейс или собственный UI framework.

---

## 10. Lighting Preview

Нужен простой realtime preview результата Normal Map.

Пользователь должен иметь возможность двигать направление источника света и визуально проверять форму объекта.

Достаточно directional light + ambient.

Preview предназначен только для проверки и не меняет экспортируемые карты.

---

## 11. Экспорт

Минимальный output:

```text
<name>_depth.png
<name>_normal.png
```

Depth:

- grayscale;
- предпочтительно 16-bit PNG.

Normal:

- RGBA PNG;
- OpenGL +Y по умолчанию;
- alpha = source alpha.

Не применять художественную color/gamma correction к normal map.

Желательно сохранять рабочее состояние Depth, чтобы ручные правки можно было продолжить после перезапуска приложения. Реализовать самым простым способом: например, sidecar/project file + сохранённая float/16-bit depth.

---

## 12. Архитектура и структура проекта

Использовать **минимальную достаточную архитектуру**: код должен быть понятным, модульным и легко изменяемым, но без enterprise-слоёв и абстракций, которые не решают практическую задачу.

Не нужно искусственно минимизировать количество файлов. Разделять код по ответственности, когда это улучшает читаемость, тестируемость или позволяет независимо менять важные части приложения. Не создавать множество микромодулей по несколько строк и не складывать несвязанные части системы в один огромный файл.

Архитектура должна позволять независимо изменять:

- Depth AI inference;
- Depth post-processing;
- генерацию Normal;
- редактор Depth;
- atlas/tile processing;
- GUI;
- экспорт и сохранение проекта.

Рекомендуемый ориентир:

```text
sprite-soul/
    app.py
    smg/
        pipeline.py
        depth/
            inference.py
            processing.py
        normal.py
        atlas.py
        editor.py
        export.py
        ui/
            main_window.py
            image_view.py
            lighting_preview.py
    tests/
        test_normal.py
        test_pipeline.py
    pyproject.toml
```

Это ориентир, а не жёсткое требование. Допускается объединять или разделять модули, если итоговая структура становится понятнее.

### Принципы поддерживаемости

- Один модуль — одна понятная зона ответственности.
- Повторяющуюся логику выносить в общую функцию или модуль.
- GUI использует общий pipeline и не дублирует алгоритмы Depth/Normal.
- Код конкретной Depth-модели отделён от обработки изображения и GUI, чтобы модель можно было заменить локально.
- Для математических преобразований предпочитать небольшие чистые функции.
- Классы использовать там, где действительно есть состояние: GUI, editor, Undo/Redo, lifecycle модели.
- Не создавать interface/factory/plugin-system только ради возможного будущего расширения.
- Для потенциально заменяемого компонента достаточно простой и стабильной границы модуля/API.
- Избегать глобального изменяемого состояния.
- Настройки, влияющие на результат, хранить централизованно и передавать явно.
- Комментарии нужны для неочевидной математики и причин решений, а не для пересказа очевидного кода.

Без практической необходимости не создавать repository layer, service layer поверх простых функций, dependency injection framework, factory hierarchy, plugin framework, десятки domain classes или собственную event system поверх PySide6.

CLI необязателен, если заметно увеличивает реализацию. Основной продукт — GUI.

Главный критерий архитектуры: **после завершения MVP другой разработчик или coding-agent должен иметь возможность изменить один компонент, не разбирая и не переписывая всё приложение**.

---

## 13. Проверки и тесты

Не нужна большая тестовая инфраструктура.

Достаточно нескольких коротких тестов критической математики:

1. flat Depth даёт normal примерно `(0, 0, 1)`;
2. slopes X/Y дают правильное направление normal;
3. OpenGL/DirectX корректно меняют Y;
4. output имеет исходные width/height;
5. output alpha совпадает с source alpha;
6. silhouette не получает сильный ложный bevel из-за прозрачного фона.

Не писать тесты для тривиального GUI/boilerplate.

---

## 14. Оптимизация под RTX 3060 6 GB

Основные меры:

- FP16 inference;
- не держать лишние модели в VRAM;
- одна Depth model;
- tiles/crops для крупных atlas;
- post-processing по возможности NumPy/OpenCV на CPU;
- освобождать ненужные GPU tensors;
- не блокировать GUI во время inference.

Не делать сложную систему управления VRAM, пока реально не возникнет необходимость.

---

## 15. Приоритет реализации

Реализовывать короткими вертикальными этапами.

### Этап 1

```text
PNG → Depth → Normal → Export
```

Добиться корректной Normal Map и точного соответствия исходнику.

### Этап 2

Добавить Depth processing и ручные кисти.

### Этап 3

Добавить GUI и Lighting Preview.

### Этап 4

Добавить tiled/atlas processing и оптимизацию VRAM, если это необходимо на реальных ассетах.

### Этап 5

Исправлять качество на реальных деревьях, зданиях и других игровых спрайтах.

Не строить функции будущих этапов заранее.

---

## 16. Критерий готовности

Продукт считается рабочим, когда пользователь может:

1. открыть PNG-спрайт или atlas;
2. получить Depth через AI;
3. поправить Depth кистями;
4. автоматически получить Normal из исправленной Depth;
5. проверить результат движущимся источником света;
6. экспортировать Depth и Normal;
7. получить карты того же размера и с тем же alpha/silhouette, что исходник;
8. выполнить это на RTX 3060 Laptop 6 GB без постоянных OOM/crash.

Визуальное качество геометрии является главным функциональным приоритетом, но код должен оставаться достаточно модульным и понятным для дальнейшего улучшения алгоритмов.
